# 렌더러 무응답 소견 — 프로파일 1회 결과 (2026-08-12)

> 발단 = 배치⑶ 검수 소견 1: 화면 전환 직후 무응답 4회·10~30초(차트/달력 진입부).
> 지시 = 프로파일 1회 후 결과 보고(사장님 도장).

## 1. 서버 축 — 무혐의 (실측)

화면 전환 진입부가 부르는 채널 14종 × 3회, :8081(복사본)과 :8080(라이브 — 사이드카 부착) 양쪽.

| 환경 | 결과 |
| --- | --- |
| :8081 복사본 | 전 채널 **1~4ms** (todayBoard 1회 57ms가 최악) |
| :8080 라이브 | 전 채널 **1~64ms** — 최악 = processLive 콜드 1회 **262ms**(사이드카 첫 open), 이후 56ms 안정 |

서버는 better-sqlite3 동기 실행이라 **느린 쿼리 1개가 전 요청을 막는 구조** — 10~30초급
정지가 서버에 있으면 이 측정에 반드시 나타난다. 없었다. **서버 축 소명.**

## 2. 렌더러 JS 축 — 정황상 무혐의

- 코워크 실측에서 **"CDP 캡처 무응답 중에도 JS는 응답"** — 메인 스레드 JS가 살아 있었다는
  뜻이라, JS 롱태스크(대량 렌더·동기 루프)로는 설명되지 않는다.
- 진입부 렌더 규모 실측: 조업달력 = 버튼 42개 · 성과 지표 SVG = 점 12 + 바 12 · 차트 =
  바 31개 — 컴포지터가 10초 막힐 규모가 아니다.
- 초기 로드는 무겁다(JS 1.6MB + 가변 폰트 2MB) — 단 이것은 **첫 로드 1회**의 비용이고
  화면 전환마다의 현상과는 축이 다르다.

## 3. 남는 용의자 — 원격 캡처(CDP screencast) 경로

소거 후 남는 것 = **원격 조작 도구의 화면 캡처 파이프라인**(CDP screencast/스크린 공유가
GPU 컴포지터 프레임을 기다리는 구간). JS 생존 + 서버 순응답 + 캡처만 정지는 이 가설과
정합한다.

## 4. 분기 — **확정(8/12 도장): "보였다"** → 원격 한정 가설 기각·계측 트랙 편성

사장님 육안으로도 멎음이 보였다 — §3의 원격 캡처 단독 가설은 **기각**. 실사용 성능 문제로
격상. 단서 누적: 배치⑶ 검수에서 4회 · **배치⑷ 검수에서 0회**(코워크 관측) — "차트 화면
일반"이 아니라 **조업달력·성과지표 진입부 국면**이 우선 용의 구간.

### 계측 배선 (같은 날 이행 — `presentation/lib/perfWatch.ts` + AppShell 기동)

| 관찰자 | 잡는 것 | 판별 |
| --- | --- | --- |
| longtask(500ms+) | JS 메인 스레드 롱태스크 | 찍히면 = JS 축(어느 화면·몇 ms 좌표 동봉) |
| 하트비트 간극(2s+) | 이벤트 루프 정지 | 찍히면 = 렌더러 프로세스 정지 축 |
| 화면 전환 마크 | 언제·어느 화면 | 멎음 시각과 대조할 좌표 |

**판별 설계의 핵심**: 멎음이 또 보였는데 위 셋에 아무것도 안 찍히면 = **컴포지터/GPU 축
확정**(JS 무혐의의 물증). 열람 = F12 콘솔 → `__perfLog()`(표) / `__perfLogCsv()`(복사용) —
localStorage 링버퍼 300건이라 새로고침에도 남는다.
