## §8. 코워크 확인요청 답변

### Q. 952 − 716 = 236. 공존 0인데 이 236이 MES 현행에도 있으면 정의상 공존 아닌가?

**A. 가설 (a) 다 — 적재 시 기존 행이 유지되고 출처 라벨만 낡은 것.** 근거는 스키마다.

```
bom_edge … UNIQUE (parent_code, child_code)   ← 확인
동일 (부모,자식) 다중 행 : 0건
```

한 간선에 두 행이 물리적으로 생길 수 없다. 그래서 **이 스키마에서 '공존'은 성립 자체가 불가능**하고, `공존 0`은 '중복이 없다'가 아니라 '중복이 있을 수 없다'로 읽어야 한다. popbom 적재가 기존 2021 행을 만나면 그 행을 그대로 두므로, MES 현행 간선인데 `source='2021'` 인 상태가 236건 남았다.

검산: popbom 1,807 + 라벨낡음 236 = **2,043** = MES 현행 2,043 ✔

- 가설 (b) 소요량이 판정 키에 관여? — **아니다.** 키는 (부모,자식)뿐. 236건 소요량 숫자 비교 불일치 **0건**
- 가설 (c) 집계 단위 차이? — **아니다.** 전체 행수 = 고유 간선 수 = 2,759 (1행 = 1간선)

> ⚠️ 자체 정정: 이 236건을 처음 진단할 때 문자열 비교(`'1.0' != '1'`)를 써 전건 불일치로 셌다. 숫자 비교로 바로잡아 위 수치를 낸다.

| 품목 마스터 전체 2,308종 | 1,183종 (51.3%) |

→ **POP_ITEM BLOB 백로그를 P2 선행조건으로 승격할 필요 없다.** 조인 한 번으로 전광판 모수의 94.1% 가 채워지고, 남는 56종만 개별 보완하면 된다.

### Q. 947/891 은 실측인가 (A1′ 종결 판단)

**실측이다.** 다만 분모를 갈라야 한다 — '지금 도는 품번'과 '품목 마스터에 있는 품번'은 다른 모수이고, A1′(마스터 품명 채우기)의 분모는 후자다.

| 모수 | 전체 | 품명 확보 | 잔여 |
|---|---|---|---|
| A. 지금 도는 품번(마스터 무관) | 947 | 891 (94.1%) | 56 |
| **B. 도는 품번 ∩ 품목 마스터** ← A1′ 분모 | **920** | **871 (94.7%)** | **49** |
| C. 품목 마스터 전체 | 2,308 | 1,183 (51.3%) | 1,125 |

→ **A1′ 회의 안건 = 「조인 승인」 + 잔여 49종.** 1,183(마스터∩품명) ≥ 871(도는∩마스터∩품명) 으로 앞선 수치와 모순 없다.

**부수 발견**: 도는 품번 중 **27종이 품목 마스터에 아예 없다**(947 − 920). 품명이 아니라 품목 자체가 빠져 있다 — 별도 안건.

**표기 정규화 가설은 기각.** 잔여가 하이픈 없는 품번·`(구형)/(신형)` 괄호에 몰려 있어 조인 실패를 의심했으나, 정규화(하이픈·괄호 제거)로 붙는 것은 **1종뿐**(`310334F850완성` → GUIDE-PIN). 나머지는 **수불에만 있고 검사 기록이 없는 품번**이라 `sqc_parts`(검사 기준)에 애초에 존재하지 않는다 — 원자재·부자재로 보이며 **품명 원천이 POP_ITEM(BLOB)뿐**이다.

### A10(비활성 되돌리기)에 대하여 — 절반은 이미 스키마에 있다

`bom_edge.active` 컬럼 주석이 그대로 **"파이프라인이 소멸 간선을 0으로 (삭제 금지)"** 다. 비활성≠삭제는 이미 설계돼 있고 지켜지고 있다(물리 삭제 경로 없음). 남는 것은 **비활성 품번에 수주·투입·검사가 다시 뜨면 의무 발행**하는 트리거 쪽뿐이며, A3(미태깅 적체)과 같은 틀이라 함께 만들면 된다. A/S 보수부품이 12개월을 넘겨 재발생한다는 지적에 동의한다.

## §9. 별건 2 — 심사일 원천이 두 곳으로 갈려 있다 (라이브 결함)

대사와 무관하나 같은 확인 과정에서 나왔다. 화면 상단 D-day 배지와 SQ 트랙이 **서로 다른 값**을 본다.

| 출처 | 값 | 표시 |
|---|---|---|
| `company_profile.auditDate` ← D-day 배지 | `2026-12-31` | D-152 |
| `app_config.sqtrack.audit_date` ← SQ 트랙 | `2026-10-15` (10월 SQ LEVEL-UP 심사) | D-75 |

`2026-12-31` 은 `src/main/database/seed.ts` 의 **데모 기본값**이며(주석에 명시), `hooks/useDday.ts` 의 폴백 상수도 같은 값이다. 아무도 실제 심사일로 고치지 않았다.

→ **매일 보는 상단 배지가 실제보다 77일 여유 있게 표시된다.** 15·25번 문서의 '10월 심사'와 어긋나는 쪽은 `company_profile` 이다.

→ 조치안: ① `company_profile.auditDate` 를 `2026-10-15` 로 정정하거나 ② D-day 가 `sqtrack.audit_date` 를 우선 보게 한다. **사장님 확인 후 반영** — 심사일이 실제로 변경됐을 가능성도 배제할 수 없다.
