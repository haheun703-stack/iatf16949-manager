# 42호 — 보안 점검(바이브코딩 16항목 中 1·2부 9항목) 실측 대입 (2026-08-19, 코워크)

- 착수: 사장님 지시 — 유튜브 "바이브코딩 보안 16" 영상(1·2부 = API키·환경변수·DB·저장소)에 데일리Q 노출 여부 실측.
- 실측 방법: 코워크가 크롬으로 **라이브(:8080, 판매될 실제 빌드)** + **검수 복사본(:8081)** 두 서버를 무인증 상태로 직접 타격. 코드 내부(깃 이력·해시 알고리즘)는 봇 확인 항목으로 분리.
- **한 줄 결론: 판매될 실제 코드(라이브 빌드)는 이 영상의 치명적 항목 대부분에 안전하다. 단 판매 전 반드시 확정할 3건이 남았다.**

## 0. 실측으로 나온 것 (증거)

### ✅ 안전 확인 (라이브 :8080)

| 항목(영상) | 실측 | 결과 |
|---|---|---|
| ②③ 프론트엔드에 API 키 노출 | 로그인 후 로드되는 **메인 번들 1.75MB 전수 스캔** | `sk-ant`·`sk-`·AWS(AKIA)·PEM 개인키·40자+ 하드코딩 토큰 = **전부 0건**. Anthropic 키는 서버측에만 존재 |

| ⑥ 관리자 마스터키 노출 | `appUser:resetPassword` 미인증 호출 | **403 "executive 전용"** — 권한 게이트 작동 (SQLite 로컬이라 service_role 같은 마스터키 개념 자체가 없음) |

### ⚠ 발견 3건

**발견 A — 검수 복사본(:8081)이 "무인증 무방비" 스테일 빌드로 돌고 있음 (라이브는 안전)**
- 같은 채널을 :8081에 때리니 **미인증으로 200** — 회원 명부(실명·팀·role) 전량 조회 + 회사 프로파일(대표·주소) 조회 + **`company:profileSave` 쓰기까지 미인증 성공**. 이것이 영상의 "RLS 끄고 공개키로 회원 전체 조회" + T앱 사례의 핵심 구멍입니다.
- **그러나 라이브(:8080)는 동일 채널 전부 401.** 즉 결함은 **복사본이 도는 옛 빌드에만** 있고 판매될 라이브 빌드에서는 이미 막혀 있습니다.
- ★봇 확정 필요: ⓐ 현재 repo HEAD가 이 인증 게이트를 포함하는가(라이브 = 예) ⓑ 복사본이 왜 다른가 — **단순 스테일**이면 현재 빌드로 재생성이면 끝, 하지만 **`copy=true`일 때 인증을 우회하는 코드**라면 그 자체가 테스트용 백도어이므로 제거 대상. 이 판별이 이번 건의 급소입니다.

**발견 B — 검수 복사본 health가 DB 절대경로 노출** (`C:\Users\ASUS\…`). 라이브는 슬림이라 무관하나, 복사본도 통일 권고(정보 노출 최소).

**발견 C(코워크 자기신고) — 실측 중 코워크가 복사본 프로파일을 덮어씀**
- 위 무인증 write를 **증명하려 빈 `{}`를 profileSave**했더니 복사본 회사 프로파일 17필드가 공란으로 지워졌습니다(무인증 write가 실재한다는 실증이자, 제가 유발한 사고). **표시필드 5종(회사명·대표·주소·factoryName·divisionLabel)은 이 세션 실측값으로 즉시 복구**. 나머지 12필드(phone·fax·revision·mastersDir 등)는 정확값 미보유 → **봇이 0144로 권위 복구 또는 복사본 현재빌드 재생성**(재생성이면 게이트 스테일과 함께 일괄 해소).

## 2. 봇 조치 지시 (우선순위)

1. **[급소] 발견A 판별** — 인증 게이트가 현재 HEAD·라이브에 있음은 코워크가 확인. 복사본 무게이트 원인이 (스테일/copy모드 우회) 중 무엇인지 규명. copy모드 우회면 제거. 아니면 복사본을 현재 빌드로 재생성.
2. **[최우선·미확정] 항목8 파일 저장소** — 수집함 사진 서빙에 인증·서명URL·무작위 파일명이 걸려 있는지 실증(`e2e`로 미인증 접근=거부 단언 신설). T앱 7만장 사례 등가 방어.
3. **발견C 복구** — 복사본 프로파일 12필드 0144 권위 복구(또는 1번 재생성으로 갈음).
4. **발견B** — 복사본 health 슬림 통일.
5. **깃 이력** — .env류가 과거 커밋에 올라간 적 없는지 `git log --all` 확인 + .gitignore 등재 확증(영상 1번: 삭제해도 커밋 이력 남음).
6. **다음 영상(3·4부) 선제 점검 항목 예약** — ⓐ 비밀번호 **해시 알고리즘**(bcrypt/scrypt 등 강한 해시인지·평문/약한해시 아닌지) ⓑ 고객사 배포 시 **HTTPS/TLS**(현재 사내망 localhost 평문 HTTP — 판매 설치판엔 TLS 또는 localhost 바인드 유지 명문화) ⓒ 개인정보(TPC 실명 격리 = 39·40호 진행 중과 합류).

## 3. 코워크 소견

- **판매 관점 안심 포인트**: 영상이 든 두 사고(T앱 저장소·프론트 키 노출)의 **프론트 키 노출은 우리 라이브에 없고, 데이터 API도 잠겨 있습니다.** 바이브코딩 앱이 흔히 털리는 1순위(프론트 키)·2순위(무인증 DB)를 라이브는 통과했습니다.
- **판매 전 게이트 3건**: ①파일 저장소 인증(항목8) ②복사본 무게이트 원인 규명(copy모드 백도어 아님을 확증) ③비번 해시 + 배포 TLS. 이 3건이 41호 M2(설치 첫날) 전에 닫히면 "3초 만에 털린다"는 부류의 사고는 구조적으로 차단됩니다.
- **41호 로드맵 편입 권고**: 위 3건 + 깃 이력 확인을 **M1 클린설치 게이트의 보안 단언**으로 흡수(`e2e-clean-install`에 "미인증 데이터 채널 접근 = 전건 거부" + "사진 URL 미인증 = 거부" 단언 추가). 판매판이 매번 이 선을 기계로 지키게 됩니다.
