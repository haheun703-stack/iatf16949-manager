# 사건 중심(Event-Centric) — 고객 불량 8D 흐름 분배맵 설계

> 작성: 2026-06-20 · 상태: **설계(코딩 전)** · 1번째 흐름 수직 슬라이스의 도메인 기반

## 0. 왜 이 문서인가 (방향 전환의 핵심)

지금까지: **문서 중심** — 규정원문 → 하위코드 순차로 405개 양식을 채우는 툴.
앞으로: **사건 중심** — "고객 불량이 들어왔다"는 현실 사건에서 출발해, 담당자가
실제 일하는 순서대로 **한 번 기록**하면 시스템이 **관련된 모든 IATF 양식에 자동 분배**하고,
빠진 필수항목은 **🔴 빨간불**로 띄운다.

> 핵심 원리: **1개 케이스 입력 → N개 양식 자동** + **🔴 = 미충족 필수항목**

이 문서는 그 N개가 **실제로 어느 양식의 어느 의미칸인지**를 정의한다(분배맵). 이게 있어야 비로소
"AI가 알아서 넣어준다"가 구현 가능해진다.

## 1. 흐름 단계 ↔ 실제 IATF 양식 (DB 실재 확인 완료)

사용자가 정의한 현실 흐름:
`고객 불량 통보접수 → 임시대책 AUDIT → 5Why & 8D 조사 → 임시대책서 → 개선대책서 → 개선적용 AUDIT → 수평전개 → 4M변경`

| # | 흐름 단계 | 산출 양식(실재 코드) | 표준화(layout) |
|---|-----------|----------------------|:---:|
| 1 | 고객 불량 통보 접수 | **H3200-01** 고객불만 접수 대응 현황 보고서 · **B1100-01** 부적합품 발생 통보서 · B1100-02 통보 관리대장 | B1100-01 ✅ / 나머지 ⬜ |
| 2 | 임시대책(봉쇄) · AUDIT | **B1100-05** 불량유출 봉쇄 작업표 · **B2100-01** 시정/예방조치 요구서(발행) | B2100-01 ✅ / B1100-05 ⬜ |
| 3 | 5Why & 8D 조사 → 근본원인 | ⚠️ **전용 8D 양식 없음** → B2100-01 원인분석 + B2300-07 인라인 공정불량 사례 시트 | ⬜ |
| 4 | 임시대책서 | ⚠️ **전용 양식 없음** → B1100-05(봉쇄) + B2100-01에 흡수 | ⬜ |
| 5 | 개선대책서 | **B2100-03** 개선 대책서 | ⬜ |
| 6 | 개선적용 AUDIT(유효성) | **B2100-12** 유효성 점검 체크시트 · **B2300-06** 유효성 평가 보고서 | ⬜ |
| 7 | 수평전개 | **B2100-11** 고객사 불량 유효성 검증 관리대장 | ⬜ |
| 8 | 4M변경 | **J3100-01** 4M 변경 의뢰서 · J3100-03 관리대장 · **B2100-08** 4M변경 내역/적용일자 | ⬜ |
| 마감 | 결과 보고/등록 | **H3200-02** 고객불만 대응 조치 결과 보고서 · **B2100-02** 시정·예방조치 등록대장 | ⬜ |

### 🔑 이 표가 증명하는 것
- **단계 ↔ 양식은 1:1이 아니다.** 한 단계가 여러 양식으로 퍼지고(1→N), 일부 단계는 전용 양식이 아예 없다(3·4번).
- **같은 사실이 여러 양식에 반복된다.** 예: "근본원인"은 B2100-01·B2100-03·H3200-02·B2300-07에 **4번** 다시 적힌다.
- → **그래서 케이스 중심(한 번 입력→분배)이 압도적으로 효율적이다.** 현재 방식은 같은 내용을 4번 손으로 옮겨 적는 셈.

## 2. 케이스 공유 사실(Case Facts) — "한 번만 입력하는 정규 필드"

흐름 전체에서 **딱 한 번** 입력하면 모든 양식으로 흘러가는 정규 데이터.

| 키 | 라벨 | 입력 단계 | 타입 |
|----|------|-----------|------|
| `customer` | 고객사 | 1 | text |
| `part_no` / `part_name` | 품번 / 품명 | 1 | text |
| `defect_desc` | 불량 내용 | 1 | textarea |
| `defect_qty` / `lot_no` | 불량수량 / LOT | 1 | number/text |
| `received_date` / `occurred_date` | 접수일 / 발생일 | 1 | date |
| `containment` | 임시대책(봉쇄) 내용 | 2 | textarea |
| `root_cause` | 근본원인 (5Why/8D 결론) | 3 | textarea |
| `corrective_action` | 개선대책 | 5 | textarea |
| `verification` | 유효성 검증 결과 | 6 | textarea |
| `horizontal_deploy` | 수평전개 대상/내용 | 7 | textarea |
| `change_4m` | 4M 변경 여부·내용 | 8 | textarea |
| `owner` / `due_date` / `close_date` | 담당자 / 회신요구일 / 완료일 | 전반 | text/date |

## 4. 완성도 / 🔴 빨간불 규칙

케이스 단위로 "이 사건은 IATF상 어디까지 완결됐나"를 양식별 신호등으로.

- 🟢 **충족**: 그 양식의 **필수 Case Fact가 모두 입력됨**
- 🟡 **진행중**: 일부 입력
- 🔴 **미충족**: 필수항목 비어있음 → "이 양식 완성하려면 `근본원인` 필요" 식 안내

예) 개선대책서(B2100-03) 필수 = customer/part + defect_desc + **root_cause** + corrective_action.
→ root_cause 비면 🔴 + "5Why/8D 조사 단계 먼저".

## 5. 데이터 모델 스케치 (다음 코딩 슬라이스)

```
cases                      한 건의 고객 불량 사건
  id, case_no(자동: QC-2026-####), customer, part_no, status, owner, created_at
case_facts                 공유 사실(한 번 입력) — key/value 또는 정규 컬럼
  case_id, fact_key, value
case_steps                 흐름 진행 상태(8단계 체크)
  case_id, step_key, status, done_at
  (산출 양식은 기존 form_submissions 재사용 — case_id FK만 추가)
form_submissions + case_id 케이스가 낳은 양식 인스턴스(이미 존재, 연결만)
```

기존 자산 재사용: 레이아웃 엔진(FormDocument), 자동넘버링(nextSerial), `process_forms` 매핑,
오늘 만든 표준형(B1100-01·B2100-01)이 이 흐름의 **첫 출력 타깃**.

## 6. 권장 구현 순서 (수직 슬라이스)

1. **이 분배맵 확정** ← 지금. (field_key 정밀 매핑은 양식 표준화와 함께)
2. **흐름이 쓰는 양식 표준화**: B2100-03, B1100-05, H3200-01/02 등에 form_fields + layout_json
   (= 기존 "양식 복제" 작업에 **목적**이 생김 — 405 무작정이 아니라 흐름이 부르는 순서로)
3. **Case 데이터모델 + 흐름 UI**: 케이스 생성 → 단계 진행 → 공유사실 입력
4. **분배 엔진**: case_facts → 각 양식 form_submission 자동 생성/채움
5. **신호등 대시보드**: 양식별 🟢🟡🔴 + 빨간불 안내

> 이 슬라이스 하나가 "1입력→N양식 + 빨간불 갭검출" 전체를 증명한다.
> 되면 다른 흐름(설계변경, 정기심사 등)은 같은 틀로 복제.

## 미확정/사용자 확인 필요

- case_no 채번 규칙(QC-/CMP- 등 prefix).
